**Trigger:** Visitor clicks a marketing link like `/lp/:slug` (or any URL with
`?reference=…`) for a paid on-chain contest. There is no `/landing/:slug` route; older
`/l/:slug` links still land, as the trigger note in [[web3-landing-to-entry]] explains.
**Actors:** Visitor → Google OAuth → Rails (`LandingPagesController` / `OmniauthCallbacksController` / `TokensController` / `ContestsController` / `MessagesController`) → Stripe → Sidekiq (`TokenPurchaseJob`) → Solana RPC (managed-wallet `mint_entry_token` + `enter_contest_with_token`) → ActionCable.
**Outcome:** `users` row with `reference = "<landing-slug>"`, a `stripe_purchases` row in status `minted` with 3 on-chain `EntryTokenAccount` PDAs (one consumed), an `entries` row in status `complete` with `onchain_tx_signature`, a `messages` row broadcast on `[contest, :messages]`.
**Preconditions:** Contest is `open`, `onchain`, and carries `chat_enabled` — a column defaulting to true (`db/schema.rb:247`). The contest's season must be live on-chain: `ContestsController#ensure_onchain_season_ready!` (`app/controllers/contests_controller.rb:2316-2320`) raises the message built by `#onchain_season_error` (`:2322-2332`) when `SeasonConfig.current_season_id` names a season the vault cannot read. Stripe enabled. Visitor not in a blocked geo state.

## Sequence

1. **Visit landing page (first touch)** — `LandingPagesController#show` (`app/controllers/landing_pages_controller.rb:7-20`).
   - `cookies[:reference] = { value: @landing_page.slug, expires: 30.days }` at `:17`, and only if the cookie is blank — an explicit `?reference=` already captured by `ApplicationController#capture_reference` (`app/controllers/application_controller.rb:497-502`) wins. The cookie lives 30 days across the funnel.
2. **Click CTA → contest show page** — `ContestsController#show` (`app/controllers/contests_controller.rb:681-688`), public because `show` is in the `skip_before_action :require_authentication` list at `:9`. It renders `app/views/contests/show.html.erb:67`, which mounts the inline matchup board partial `contests/turf_totals_board`.
3. **Guest selects 6 picks, attempts to enter** — the board's `confirmEntry()` (`app/views/contests/_turf_totals_board.html.erb:1572-1586`). Picks live in Alpine state (`selections` / `selectionOrder`); no server cart is persisted yet for guests. The first thing `confirmEntry` does after its re-entry guard is read `sess.isGuest` and bounce to `showLoginModal()` (`:1580-1585`).
4. **Auth modal opens at the `credentials` step** — `showLoginModal()` (`app/views/contests/_turf_totals_board.html.erb:940-953`) calls `Alpine.store('modals').open('auth', { step: 'credentials', mode: 'signup', … })`. The wizard partial is `app/views/modals/_auth.html.erb`, whose steps are enumerated in its header comment at `app/views/modals/_auth.html.erb:6-16` (a deliberate comment citation — that list is the authoritative step machine); the credentials pane shows whenever `isCredentialsStep` is true (`:57-63`, bound at `:227`). Before any external redirect the cart is snapshot by `saveCartForRedirect()` (`app/views/contests/_turf_totals_board.html.erb:959-969`) into **`localStorage`**, not `sessionStorage` — it has to survive the magic link opening in a NEW TAB, and the method's own comment says so.
5. **"Sign up with Google" clicked** — `loginGoogle()` (`app/views/modals/_auth.html.erb:93-99`) dispatches the `auth-google-click` window event at `:96`. The board hears it and runs `loginWithGoogle()` (`app/views/contests/_turf_totals_board.html.erb:1039-1089`), which opens `/auth/google_popup` in a 500×650 popup. If the popup is blocked it falls through to `googleFullPageRedirect()` (`:1093-1107`), which re-saves the cart and full-page POSTs `/auth/google_oauth2`. With no board mounted (navbar "Sign in"), the modal runs its own `openGooglePopup()` (`app/views/modals/_auth.html.erb:100-126`) instead.
6. **Google round-trip + OmniAuth callback** — `OmniauthCallbacksController#create` (`app/controllers/omniauth_callbacks_controller.rb:27-197`). The server re-checks the id_token against Google's tokeninfo endpoint through `GoogleOauthValidator` before trusting `auth.info.email` (`:42-47`; OPSEC-005). `User.from_omniauth(auth, email_verified: true)` at `:98` creates the row (`app/models/user.rb:199-243`). The `after_create :generate_managed_wallet!` declaration at `app/models/user.rb:126` runs `User#generate_managed_wallet!` (`:580-608`), which derives an ed25519 managed wallet locally — no RPC. The `after_commit :enqueue_onchain_account_setup, on: :create` declaration at `:130` runs `User#enqueue_onchain_account_setup` (`:822-824`), which enqueues `CreateOnchainUserAccountJob` to create the on-chain `UserAccount` PDA + username asynchronously.
7. **Reference attribution + redirect to tokens-buy** — still inside `OmniauthCallbacksController#create`: `app/controllers/omniauth_callbacks_controller.rb:145-148` copies `cookies[:reference]` onto `users.reference` with `update_column` and deletes the cookie. `set_app_session(result)` at `:164` sets `session[:turf_user_id]` + `session[:session_token]` (`app/controllers/application_controller.rb:39-53`). The landing choice is at `app/controllers/omniauth_callbacks_controller.rb:187`: an explicit `return_to` carried from the /signin card (a claim-mode landing page's confirmation) wins; otherwise a brand-new signup that already has a wallet goes to `tokens_buy_path`; one still owing wallet setup goes to `contests_path` (the lobby), because `/tokens/buy` sells web2 entry tokens a wallet-less account cannot pay for. In popup mode `#finish_oauth` (`:213-227`) renders a closer page that postMessages the result instead of redirecting, and the contest tab reloads and rehydrates the cart from `localStorage`.
8. **In-modal token pack picker → Stripe Checkout** — `TokensController#stripe_checkout` (`app/controllers/tokens_controller.rb:18-100`). The user picks `trio`, 3 tokens for $49 — the packs are a frozen constant whose entries carry `quantity` and `price_cents` (`app/models/stripe_purchase.rb:15-22`). `stripe_checkout` builds `metadata = { kind: "tokens", user_id, pack_id, quantity, wallet_address, contest_slug }` (`app/controllers/tokens_controller.rb:68-75`) and a `success_url` of `/tokens/processing?session_id={CHECKOUT_SESSION_ID}&contest=<slug>` (`:64-66`), then calls `Stripe::Checkout::Session.create` at `:82`. Before any of that, `#mint_budget_refusal` refuses the purchase outright when turf-vault's per-window mint cap cannot cover the pack — above the cap a mint needs three signatures the server does not hold, and this job charges before it mints, so the only useful refusal is the one that happens before the card (see `docs/SOLANA.md`). The JSON branch returns `{ url: session.url }` at `:92` rather than redirecting, because a fetch that followed the 302 would consume the checkout session before the user saw it. The client half is `tokenCheckoutSubmit` (`app/views/tokens/_pack_button_styles.html.erb:13-41`), whose `window.open` of a blank `_blank` tab runs synchronously inside the click at `:14`, and which then sets `newTab.location.href` to the returned URL at `:32`.
9. **Stripe payment → webhook** — `Webhooks::StripeController#create` (`app/controllers/webhooks/stripe_controller.rb:8-62`); CSRF and authentication are skipped by the `skip_before_action` block at `:3-6`. `Stripe::Webhook.construct_event` verifies the signature at `:14`. The `case event.type` dispatch at `:34-35` routes `checkout.session.completed` to `#handle_checkout_completed` (`:66-108`), where `StripeCheckoutValidator` re-fetches the session and asserts `payment_status` / `livemode` / `kind` / `amount` (`:75` — OPSEC-008/032/033). Only validated metadata reaches `TokenPurchaseJob.perform_later(...)` at `:89`.
10. **On-chain token mint (the "minted" step is real on-chain, not DB)** — `TokenPurchaseJob#perform` (`app/jobs/token_purchase_job.rb:36-177`). The mint loop at `:123-135` calls `Solana::Vault#mint_entry_token(wallet_address:, source:, source_ref:)` (`app/services/solana/vault.rb:2778`) once per token. `source_ref` is `"#{purchase_type}:#{purchase.id}:#{i}"` (`app/jobs/token_purchase_job.rb:124`) — the PURCHASE row id, not the Stripe session id. Each mint creates an on-chain `EntryTokenAccount` PDA owned by the user's managed wallet. Under the v0.26 shape each mint first checks the window's remaining budget and raises `MintWindowCapReachedError` rather than broadcasting a transaction the cap has doomed; the purchase goes `failed`, an `ErrorLog` is filed against it, nothing is auto-refunded, and a re-run after the window rolls resumes at `already_minted` and completes the order. Signatures persist to `stripe_purchases.mint_tx_signatures` after every single mint (`:133`), so a mid-loop crash resumes at `already_minted = signatures.length` (`:115-117`). On success `purchase.mark_minted!(signatures)` runs at `:138`.
11. **Entry resumption (no Stripe redirect for the user)** — `/tokens/processing` is the Stripe `success_url`, and its Alpine factory's `start()` (`app/views/tokens/processing.html.erb:82-151`) hands control back two ways: a `BroadcastChannel('tt-tokens')` post at `:96-105` and a `window.opener.postMessage` fallback at `:109-119`. The contest tab attaches both listeners in the board's `init()` (`app/views/contests/_turf_totals_board.html.erb:241-313`), which flips the auth modal to step `tokens-confirming` at `:259-271` and calls `pollTokenStatus(sessionId)` at `:273`. `pollTokenStatus()` (`:1276-1362`) polls `GET /tokens/status` every 1.5s at `:1287`, served by `TokensController#status` (`app/controllers/tokens_controller.rb:462-504`). When the mint lands the modal moves to step `tokens-minted` (`app/views/contests/_turf_totals_board.html.erb:1307-1315`), which renders the in-modal Hold to Confirm button.
12. **Hold to Confirm fires entry submission** — the `hold-confirm-entry` window event runs `confirmEntry()` again. The web2 (managed-wallet) branch POSTs `/contests/:slug/enter` at `app/views/contests/_turf_totals_board.html.erb:1763-1766`. The cart picks reached the server earlier through `replaySelectionsToServer()` (`:1112-1129`), driven either by `afterLoginSuccess()` (`:1390-1391`) or by the cart hydration inside `init()` (`:481-508`) — which is why they survive the Stripe detour: by then they are cart rows in Postgres. Token consumption is server-side. `ContestsController#enter` (`app/controllers/contests_controller.rb:746-919`) runs `Entries::ManagedEntry#call`, whose `#fund!` (`app/services/entries/managed_entry.rb:151-230`) resolves `@user.next_unconsumed_entry_token_for(address)` at `:169` and calls `Solana::Vault#enter_contest_with_token` at `:177` (definition `app/services/solana/vault.rb:2358`) — one atomic on-chain instruction that consumes the token PDA, creates the entry PDA, and awards seeds. `Entries::ManagedEntry#finalize!` (`app/services/entries/managed_entry.rb:241-267`) then runs `entry.confirm!(tx_signature:, onchain_entry_id:)` at `:242`, transitioning the entry cart → complete.
13. **Redirect lands on contest page** — `ContestsController#enter` returns `redirect: contest_path(@contest)` in its JSON body (`app/controllers/contests_controller.rb:906`). There is no `tokens-submitted` step: on success `confirmEntry()` calls `Alpine.store('solanaModal').resolveEntry(...)` (`app/views/contests/_turf_totals_board.html.erb:1815-1819`), which REPLACES the auth wizard with the shared on-chain "Entry Confirmed" resolution card — a thin local adapter that delegates to the engine block `studio/modals/blocks/entry_confirmed` (`app/views/modals/blocks/_entry_confirmed.html.erb:94`), the same card the web3 path resolves to. The tokens partial says so outright in its header comment (`app/views/modals/auth/_tokens.html.erb:14-17`, cited deliberately: the comment is what documents the absent step). The user then lands on `ContestsController#show`, which renders `contests/chat_panel` at `app/views/contests/show.html.erb:101`.
14. **Send first chat message** — the chat panel's `send()` (`app/views/contests/_chat_panel.html.erb:221-265`) POSTs JSON `{ message: { body } }` to the `data-post-url` written by `contest_messages_path` at `:38`. Route: `resources :messages` nested under contest (`config/routes.rb:385`). Handler: `MessagesController#create` (`app/controllers/messages_controller.rb:8-33`). Gates: the `require_chat_enabled` before_action declared at `:5` (definition `:135-138`), and `@contest.chat_participant?(current_user)` at `:9` (definition `app/models/contest.rb:1051-1055` — admin OR an active/complete entry). The per-user 5-messages-per-15-seconds limit is `MessagesController#posting_too_fast?` (`app/controllers/messages_controller.rb:142-147`), checked at `:13-15`.
15. **Real-time broadcast** — the `after_create_commit :broadcast_new_message` declaration at `app/models/message.rb:61` runs `Message#broadcast_new_message` (`:87-96`), which calls `broadcast_prepend_to([contest, :messages], target: "contest_#{contest_id}_messages", partial: "messages/message")` at `:88-93`. The browser subscribes through `turbo_stream_from` at `app/views/contests/_chat_panel.html.erb:41`. Turbo Streams over ActionCable — no custom channel class.

## Data touched

- `users` (insert) — `email`, `name`, `provider="google_oauth2"`, `uid`, `email_verified_at`, `username` (auto-gen), `web2_solana_address`, `encrypted_web2_solana_private_key`, `session_token`. `reference` is written immediately afterwards with `update_column` inside `OmniauthCallbacksController#create` (`app/controllers/omniauth_callbacks_controller.rb:146`).
- `cookies[:reference]` (read/write) — seeded by `LandingPagesController#show` (`app/controllers/landing_pages_controller.rb:17`), seeded from the URL by `ApplicationController#capture_reference` (`app/controllers/application_controller.rb:501`), and deleted in `OmniauthCallbacksController#create` (`app/controllers/omniauth_callbacks_controller.rb:147`).
- `session[:turf_user_id]` + `session[:session_token]` (write) — `ApplicationController#set_app_session` (`app/controllers/application_controller.rb:39-53`).
- `stripe_purchases` (insert + updates) — `stripe_session_id`, `quantity=3`, `price_cents=4900`, `status: pending → minted`, and `mint_tx_signatures` as an incremental JSON array written by `TokenPurchaseJob#perform` (`app/jobs/token_purchase_job.rb:133`). The row itself is created at `:95-101` when the webhook is the first thing to reach the job.
- `entries` (insert as `cart`, then update to `complete`) — cart rows arrive through `replaySelectionsToServer()` (`app/views/contests/_turf_totals_board.html.erb:1112-1129`); the transition to complete is `entry.confirm!` inside `Entries::ManagedEntry#finalize!` (`app/services/entries/managed_entry.rb:242`). `onchain_tx_signature`, `onchain_entry_id`, `entry_number` written.
- `selections` (insert × 6) — `replaySelectionsToServer()` POSTs `toggle_selection` once per saved matchup id (`app/views/contests/_turf_totals_board.html.erb:1116-1124`).
- `transaction_logs` (insert) — `TokenPurchaseJob#perform` records one per purchase (`app/jobs/token_purchase_job.rb:151-159`) with `type: "token_purchase"` and `direction: "credit"`.
- `outbound_requests` (insert) — every Stripe API and Solana RPC call in this flow auto-logs through `Stripe::Instrumentation` + `Solana::ClientLogger`.
- `messages` (insert) — `body`, `user_id`, `contest_id` set in `MessagesController#create` (`app/controllers/messages_controller.rb:17`). `hidden_at` stays `NULL`.
- `localStorage.pendingContestEntry` (browser-only) — the picks snapshot used for resumption, written by `saveCartForRedirect()` (`app/views/contests/_turf_totals_board.html.erb:961-966`) and consumed once, with a 30-minute freshness guard, by `init()` (`:472-479`). It is localStorage, not sessionStorage, so the magic-link return survives landing in a different tab.
- on-chain: `EntryTokenAccount` PDA × 3 via `Solana::Vault#mint_entry_token` (`app/services/solana/vault.rb:2778`; signer: vault admin keypair). `EntryAccount` PDA + `UserAccount` PDA seeds bump via `Solana::Vault#enter_contest_with_token` (`:2358`; signers: vault admin + the user's managed keypair). The `UserAccount` PDA itself is created asynchronously by `CreateOnchainUserAccountJob`.
- external: Google `tokeninfo` GET (OPSEC-005), Stripe `Checkout::Session.create` + webhook + `Checkout::Session.retrieve` (the validator's re-fetch).

## Failure modes

- **Reference cookie collision** — `LandingPagesController#show` writes the cookie only when `cookies[:reference].blank?` (`app/controllers/landing_pages_controller.rb:17`), and `ApplicationController#capture_reference` likewise returns early when one is present (`app/controllers/application_controller.rb:499`). First touch wins; later landing visits leave the cookie alone. → silent, and correct.
- **Google email already linked to an unverified existing user** — `User.from_omniauth` returns `:requires_verification` (`app/models/user.rb:215`). `OmniauthCallbacksController#create` surfaces "sign in with your password and verify your email before linking Google" (`app/controllers/omniauth_callbacks_controller.rb:140-141`). A wallet-secured collision cannot prove email ownership with a password, so it is stashed and routed to a wallet login instead (`:109-139`). No silent merge (OPSEC-005). The reference stays in the cookie for the eventual signup.
- **Profile not complete** — N/A on this app. `User#ensure_username` auto-fills the username through `Studio::UsernameGenerator.generate` (`app/models/user.rb:766-781`), so `User#profile_complete?` (`:297-299`) is true from the moment the row exists.
- **Stripe webhook signature mismatch / replay** — `Webhooks::StripeController#create` returns 400 on bad JSON or a bad signature (`app/controllers/webhooks/stripe_controller.rb:15-20`) and 200 + a log line on a test event in production (`:29-32`). `#handle_checkout_completed` drops a mismatched payment_status / livemode / kind / amount with a logged `validator_rejected` (`:77-80`).
- **Partial mint failure (1 of 3 tokens minted, RPC crashes)** — `TokenPurchaseJob#perform` persists each signature before continuing (`app/jobs/token_purchase_job.rb:133`). On the Sidekiq retry the loop resumes at `already_minted` (`:115-123`), and `purchase&.mark_failed_unless_minted!` in the rescue (`:175`) never downgrades a row that already reached `minted`. The job also short-circuits outright on a `minted` or `refunded` row (`:70-73`) — the OPSEC-009 idempotency stop.
- **User refreshes during the Stripe round-trip** — the cart picks are already POSTed to the server as cart-status `entries` + `selections` rows by `replaySelectionsToServer()` (`app/views/contests/_turf_totals_board.html.erb:1112-1129`), replayed from the hydration block in `init()` (`:481-508`). The processing tab's `BroadcastChannel` cannot reach a closed contest tab, but the next contest visit reads the cart rows back from the DB. The on-chain mint completes regardless — the job is async.
- **`/tokens/status` polling times out (>45s)** — `pollTokenStatus()` flips the modal to step `tokens-error` with "Payment cleared but the on-chain mint is still settling" (`app/views/contests/_turf_totals_board.html.erb:1349-1358`).
- **`ContestsController#enter` race — contest full mid-flight** — the `with_lock` in `Entries::ManagedEntry#call` (`app/services/entries/managed_entry.rb:77`) runs `entry.assert_enterable!` (`:82`) BEFORE any consume, and its `active_count >= contest.max_entries` check (`app/models/entry.rb:157-158`) raises "Contest is full"; the response 422s and the modal surfaces the error with the token unconsumed.
- **Chat message rate-limit hit** — `MessagesController#create` returns 429 when `posting_too_fast?` is true (`app/controllers/messages_controller.rb:13-15`). The user sees "You're posting too fast" in the composer.
- **ActionCable broadcast failure** — `Message#broadcast_new_message` rescues and logs to `ErrorLog` (`app/models/message.rb:94-95`), so the controller request still returns `{ ok: true }`. Other subscribers miss the message, and so does the poster: the panel renders from the broadcast, not from the POST response. → Inspect `error_logs` for `Message` targets.
- **Chargeback / refund post-mint** — `Webhooks::StripeController#handle_dispute` (`app/controllers/webhooks/stripe_controller.rb:112-123`) and `#handle_refund` (`:127-136`) set `payment_risk_flag` and call `User#freeze_for_payment_risk!` (`app/models/user.rb:515-519`). The frozen account can still read but every write is refused (`FrozenAccountGuard`); an operator unfreezes from `/admin/users`, which calls `User#unfreeze!` (`:521-524`) and records an `AccountFreezeEvent`.
